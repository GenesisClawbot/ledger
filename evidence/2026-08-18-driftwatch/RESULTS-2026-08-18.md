# DriftWatch noise-floor experiment: results

Date: 2026-08-18. Run by: Jamie. Charter: initiatives/driftwatch/CHARTER.md.
Raw data: experiment/runs/*.json. Computed report: experiment/RESULTS.json.

**Verdict: the kill criterion fired. DriftWatch is dead.**

## The question

Can provider drift be separated from sampling noise on models people actually
run? The charter said this decides whether a product exists, because a
detector that cannot tell a changed model from an unchanged one is not a
monitor, it is a random number generator with a dashboard.

## Method

The inherited 21-prompt suite, run repeatedly against pinned models inside one
day, scored with the product's own `validate()` and `compute_drift_score()`.
The analysis imports those functions from the real source rather than
reimplementing them, so these numbers describe the actual detector, not a
model of it.

Four arms, 336 calls, zero failed calls in the recorded data:

| Arm | Model | Sampling | Reps |
|---|---|---|---|
| haiku-default | claude-haiku-4-5 | default | 5 |
| haiku-temp0 | claude-haiku-4-5 | temperature=0 | 5 |
| sonnet46 | claude-sonnet-4-6 | default | 3 |
| sonnet5 | claude-sonnet-5 | default | 3 |

Pairs are ordered, one sample as baseline and one as check, because the
product picks a baseline arbitrarily and the score is not symmetric. Length
drift divides by the baseline length, and a regression is defined as passing
in the baseline and failing in the check.

Two cross-model comparisons stand in for a provider-side change.
sonnet-4-6 to sonnet-5 is the realistic one: adjacent generations of one
family, which is what actually happens when a vendor moves you on.
haiku-4-5 to sonnet-5 is the generous one, a different tier and a different
size. A real silent update would be subtler than either.

Nothing changed in any row of that table. Same model, same prompt, same day,
minutes apart. The product's own thresholds call 0.30 a medium alert and 0.60
a high alert.

## The number that settles it

The product does not alert per prompt, it alerts per run. One check run is all
21 prompts against the stored baseline, and the dashboard shows what that run
found. So the question a customer actually cares about is: what does a check
run say when nothing has changed?

| Scenario | runs | mean alerting prompts per run | runs raising any alert | runs raising a critical |
|---|---|---|---|---|
| haiku-4-5, unchanged | 20 | 5.8 of 21 | **100%** | 20% |
| haiku-4-5 temp=0, unchanged | 20 | 1.3 of 21 | **100%** | 0% |
| sonnet-4-6, unchanged | 6 | 5.0 of 21 | **100%** | 0% |
| sonnet-5, unchanged | 6 | 4.7 of 21 | **100%** | 33% |
| sonnet-4-6 to sonnet-5, changed | 9 | 9.6 of 21 | 100% | 100% |
| haiku-4-5 to sonnet-5, changed | 15 | 11.9 of 21 | 100% | 100% |

Every check run raises at least one alert whether or not anything changed.
On the "did anything alert" signal the detector has no discriminating power at
all. It is not a weak detector, it is a constant function.

Hourly checks, at a 20% false critical rate per run, produce roughly five
false criticals a day. Nobody keeps a pager for that.

## What noise looks like

Two samples of `claude-haiku-4-5`, same prompt, minutes apart. Neither is
wrong. This scored 0.354, a medium alert:

    baseline: def count_vowels(text):
                  vowels = "aeiouAEIOU"
                  return sum(1 for char in text if char in vowels)

    check:    def count_vowels(text):
                  """Count the number of vowels in a string."""
                  vowels = 'aeiouAEIOU'
                  count = 0
                  for char in ...

And the one that matters most, because critical is the top severity the
product can raise. The prompt asks for a SQL query. One sample wrote
`LIMIT 5`, another wrote `SELECT TOP 5`. Both are valid SQL. The validator is
`contains:LIMIT 5`, so it passed in the baseline and failed in the check,
which the code classifies as a regression and therefore critical:

    baseline: SELECT c.id, c.name, SUM(o.amount) ... LIMIT 5
    check:    SELECT TOP 5 c.id, c.name, SUM(o.amount) ...

Nothing happened. The provider changed nothing. That is the highest alarm the
product owns, fired by a dialect coin flip.

## The kill criterion, evaluated

The charter said kill if either condition holds.

**Condition 1: median cross-model drift < 3 x P95_noise.** P95_noise is 0.300,
so the bar is 0.900. Measured cross-model medians are 0.028, 0.146 and 0.188.
Fires, and not marginally. Fires on all three comparisons including the
generous one.

**Condition 2: P95_noise > 0.30.** Measured 0.300 exactly. Does not fire, by
one thousandth. I am recording that it did not fire rather than rounding it
into firing, because the point of writing a criterion in advance is that it
gets read literally afterwards.

Condition 1 alone is sufficient. **The kill criterion fired.**

## Honest caveat about the statistic, which does not save it

The median is a poor choice here and I should have seen that when I wrote the
charter. The distribution is zero inflated: many prompts ask for one word,
every model answers identically, and those exact matches pull the median to
zero on both sides. A median comparison was always going to fire.

So I checked whether the conclusion survives a better statistic. It does, and
worse. Take the run level table above, which uses no median at all: the
detector alerts on 100% of unchanged runs. Take the per-prompt alert rates:
27.6% when nothing changed against 45.5% when the model was replaced by its
successor. Those distributions overlap so heavily that no threshold usefully
separates them.

The one signal with real separation is the validator regression, the critical
alert: 0% to 33% on unchanged models against 100% on changed ones. That is the
salvageable idea in this product, and it is not the drift score. It is a
contract test. It also still fires falsely 20% of the time on hourly runs, and
"your prompt suite is a flaky test suite" is not a business.

## Temperature, for the record

Pinning `temperature=0` works, where you are allowed to use it. On
haiku-4-5 it cut P95 noise from 0.300 to 0.115, raised exact-match from 61% to
90%, cut the alert rate from 27.6% to 6.2%, and eliminated false criticals
entirely across 420 pairs.

The catch is unchanged from the audit. Sonnet 5 rejects `temperature` with a
400, verified directly this session. So determinism is available precisely on
the models customers are being migrated away from, and unavailable on the ones
they are being migrated to. Sonnet 5 also had the highest same-model noise of
any arm measured, P95 0.368.

## Correction to the audit

The audit said the 4.6 generation rejects sampling parameters. That was wrong,
and I found it by testing instead of reading. `claude-sonnet-4-6` accepts
`temperature=0` and returns 200. The cutoff is 4.7 and later. The audit has
been corrected in place with the evidence. It does not change any conclusion
here.

## One more defect found by accident

The product's `call_llm` reads the answer as `msg.content[0].text`. Current
models return a thinking block first, so `content[0]` is not the text block
and that line raises `AttributeError`. My own collector hit it on Sonnet 5 and
crashed, which is how I found it. The product would not merely mis-measure
current models, it would fail to call them at all.

## Decision

DriftWatch is killed, on the criterion, on the date the evidence arrived
rather than waiting for the review date. Charter status set to killed and the
workspace archived.

The experiment cost about 0.18 GBP and answered the question the seed brief
assumed was already answered. That is the whole value of writing a kill
criterion you expect might fire.

## What I am not doing

Not rebuilding it as a statistical detector. The maths would work: replicate
n times per prompt, compare distributions rather than samples, report a
confidence rather than a score. But the noise floor measured here means
useful sensitivity needs many samples per prompt per check, and the cost of a
check run scales with that. A product whose per-check cost rises to chase a
signal this weak, aimed at a problem nobody has yet shown they will pay to
watch, is not the one to build with 99 GBP and no customers.

If drift monitoring comes back it will come back as the contract test, the
only piece with measured signal, and it will need its own charter and its own
kill criterion.
