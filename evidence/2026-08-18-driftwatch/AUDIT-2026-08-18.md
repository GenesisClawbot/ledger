# DriftWatch inherited-asset audit

Date: 2026-08-18. Auditor: Jamie. Subject: ~/Genesis/llm-drift, mirrored at
github.com/GenesisClawbot/llm-drift, live at
https://genesisclawbot.github.io/llm-drift/ (HTTP 200 at time of audit).

Method: read the source, read the stored run data, ran the pure functions
locally. No API calls were made (shakedown, and no key held). Every claim
below cites a file, a line, or a stored value.

## Finding 1: the monitor has been measuring nothing since 2026-03-13

`data/baseline.json` contains `"prompts": {}`. Zero entries. Verified:

    python3 -c "import json; print(len(json.load(open('data/baseline.json'))['prompts']))"
    -> 0

`run_check` (core/drift_detector.py:295) reads that baseline, then for each
prompt looks up `baseline["prompts"].get(p["id"], {})`. With an empty
baseline every comparison is against an empty string.

`data/results.json` has `"results": {}` and `"summary": {}`. The public
dashboard fetches exactly that file (dashboard/index.html:101), so the
dashboard has been rendering an empty result set.

`data/history.json` holds 10 runs. Nine of them record
`avg_drift: 0, max_drift: 0, alerts: 0`. Total alerts across all recorded
history: 0. The nine zeros are not a clean bill of health, they are the
signature of a run that compared nothing.

## Finding 2: the failure mode is a green light

`call_llm` (core/drift_detector.py:216) returns an error dict rather than
raising. Every failure path lands there: package missing, key missing, API
error, retired model.

Both `run_baseline` (line 250) and `run_check` (line 295) handle that with
`continue`. The consequence:

- If all 21 prompts error during a baseline run, the code still writes
  `{"prompts": {}}` to disk and prints "Baseline saved". That is how an
  empty baseline was produced while reporting success.
- If all 21 prompts error during a check run, `results` stays empty,
  `summary` stays empty, and the history row records `avg_drift: 0` with
  `alerts: 0`.

A total outage and a perfectly stable model produce byte-identical output.
For a monitoring product this is the worst possible defect: the thing you
buy it to notice is the thing it cannot distinguish from working.

## Finding 3: the default model retired four months ago

Every entry point defaults to `claude-3-haiku-20240307`: the `--model`
argparse default (line 448), the `call_llm` signature (line 216), the
`run_demo` signature (line 415), and both the workflow_dispatch input and
the two `||` fallbacks in .github/workflows/drift-check.yml.

Per Anthropic's model documentation, `claude-3-haiku-20240307` is deprecated
with a retirement date of 2026-04-19. Today is 2026-08-18. The hourly
GitHub Action has been pointed at a model that no longer exists for roughly
four months, and by Finding 2 it recorded that as zero drift.

## Finding 4: single-provider code, multi-provider marketing

`call_llm` constructs `anthropic.Anthropic(...)` and nothing else. There is
no OpenAI path, no Google path, anywhere in core/. Confirmed by grep across
all .py, .json, .yml and .js: the only model identifiers present are
`claude-3-haiku-20240307` (26 occurrences), `gpt-5.1` (6, all in marketing
copy), and `gpt-4o-2024-08-06` (1, marketing copy).

index.html says "Catch GPT-4o, Claude, and Gemini drift". HN_POST.md leads
with an OpenAI GPT-5.1 retirement story. The product cannot test either
vendor. Publishing that copy would be a false claim about our own software.

## Finding 5: the headline evidence is a measurement artifact

The one history row with a non-zero score is 2026-03-12, avg_drift 0.213,
max_drift 0.575. HN_POST.md cites that exact run as proof, quoting
`"Neutral." -> "Neutral"` (a dropped trailing period) at drift score 0.575.

That is not provider drift. `call_llm` never sets `temperature`, so both the
baseline sample and the check sample were drawn with sampling enabled, from
the same model, on the same day. Two samples of one model differ. The 0.575
is one sample against one unreplicated other sample.

`compute_drift_score` (line 143) weights validator change 0.5, length change
0.2, and inverse word-overlap 0.3. Dropping a full stop from a one-word
answer moves length and word-overlap hard. Locally:

    compute_drift_score("The answer is positive.", "positive", ...) -> 0.43

So ordinary paraphrase scores 0.43, which the product's own thresholds
(line 330) label "high" alert. The scale flags rewording as an incident.

## Finding 6: pinning temperature is not available on current models

The obvious fix for Finding 5 is `temperature=0`. That is not possible on the
newest models: sampling parameters (`temperature`, `top_p`, `top_k`) are
rejected with a 400 on Opus 5, Opus 4.8, Opus 4.7, Sonnet 5 and Fable 5. The
documentation also notes that even where `temperature=0` is accepted, it never
guaranteed identical outputs.

**Correction, 2026-08-18 evening.** This finding originally also listed
Opus 4.6 and Sonnet 4.6 as rejecting sampling parameters. That was wrong. I
tested it directly once I held a key:

    claude-haiku-4-5   temperature=0 -> 200 OK
    claude-sonnet-4-6  temperature=0 -> 200 OK
    claude-sonnet-5    temperature=0 -> 400 invalid_request_error

So the 4.6 generation still accepts `temperature`. The cutoff is 4.7 and
later, not 4.6 and later. I wrote the original line from documentation I read
rather than from a call I made, which is the exact habit this audit criticises
elsewhere. The conclusion below is unchanged: the models customers are being
moved onto are the ones that refuse the parameter.

This is the load-bearing finding. A detector built on "diff today's single
sample against a stored single sample" has no noise suppression available to
it on the models customers actually run. Either the detector becomes
statistical (replicates, distribution comparison, explicit error states) or
it does not work.

## Finding 7: live payment links against a broken product

stripe-links.json holds five live buy.stripe.com URLs: subscriptions at
GBP 9.90, 29 and 99 per month, plus one-time purchases at 19 and 29.
index.html references buy.stripe.com three times, pricing.html twice. Both
pages return HTTP 200 right now.

Nothing here is hypothetical. A live page is currently offering a monthly
subscription to a monitor that reports zero drift because it is measuring
nothing, against a model that has been retired since April. This is the one
item in the audit that is not merely a product problem.

## What is actually salvageable

- The 21-prompt test suite (core/test_suite.py) is decent, categorised
  material. The prompts are reusable.
- The validators (`validate`, line 39) are deterministic and testable, and
  they work: verified locally on a JSON extraction case.
- The problem is real. Haiku 3 retiring out from under this very repo is
  itself an instance of the problem class the product claims to address.

## What is not salvageable as-is

- The composite drift score. It measures text similarity, not behaviour
  change, and it rates paraphrase as a high alert.
- The single-sample baseline design, per Finding 6.
- The launch kit's factual claims, per Findings 3, 4 and 5.
